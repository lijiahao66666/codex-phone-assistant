# 附件上传优化验证

本轮代码先提交推送、整合 `main`，再由 owner/model 任务统一发布；以下为本地验证记录，不代表 iPhone 或公网已验收。

点击发送后，文字和附件立即移入聊天里的本地消息，输入框清空并可继续编辑。附件在后台上传，输入框底部不显示上传文字或百分比；待送达消息只显示小钟图标。失败保留原始文件，错误和恢复草稿操作显示在该条消息内。结果未知的消息不会自动重发，也不会继续发送排在其后的消息。

每个文件先用首片测试 gzip 收益，仅传输更小的结果。收益不足 2% 时后续分片直接传原始字节，减少重复压缩开销。并发开始的第二片可能已经在压缩。没有缩放、转码、图片质量调整或文件内容修改。JPEG、ZIP、DOCX、MP4 等已经压缩的数据通常无法再显著缩小，提速需要减少请求往返和重叠传输。

新电脑连接器声明支持后，H5 使用 512 KiB 分片、最多两片并发。旧连接器或重新连接后尚未声明能力时，保持 128 KiB 和串行上传。接收端允许后一片先到，按序落盘后确认；取消、超时及写盘失败会拒绝等待中的请求，完成操作必须等待全部分片确认。保留每个文件 20 MiB、30 秒空闲和 120 秒总时长限制。

本地接收端 18 项测试通过，覆盖 512 KiB 原始字节一致、混合大小、顺序、并发、慢速进度、取消和超时。乐观发送与失败恢复 10 项测试通过，覆盖消息立即显示、队列顺序、未知结果不重发、任务及设备切换隔离、并发失败取消、恢复原始附件后手动重发。

隔离 HTTP 实验使用 256 KiB 文件、8 个 32 KiB 分片，并对每个响应增加 30 毫秒延迟。本轮暂存树测试中，串行为 2376 毫秒，两片并行为 1510 毫秒。本机网络栈额外开销明显，实验数值不能用作真机速度承诺。

统一版本发布后需测试 iPhone 图片和常用文件的发送耗时，并检查任务切换后的后台消息。503 错误和旧桌面助手的回退行为也尚待验收。公网测试须使用独立临时 host 和隔离上传目录，不得重新配对用户正在使用的电脑。

上传提交的独立暂存树已运行完整测试，115 项全部通过。与 owner/model 及配对恢复的组合测试另行记录。

## 组合服务的上传等待预算

2026 年 11 月 7 日继续合并 owner/model 服务时，真实 HTTP 测试发现过 503。首个小 gzip 分片可以比前一片大文件更早到达，此时它要等待前一片传输和按序落盘。原来的 10 秒普通请求超时也用于上传响应，可能在文件仍正常传输时取消整个上传。

隔离掉项目逻辑后，本机 512 KiB 原生 HTTP 请求仍耗时 3788 毫秒；699052 字节的纯 WebSocket 消息传输耗时 5826 毫秒（启用压缩）或 7211 毫秒（关闭压缩）。项目中的磁盘确认约为 6 毫秒。这些本机结果说明仅改测试的 fetch 调用不能消除等待，也不代表公网或手机速度。

上传响应现使用独立的 30 秒预算，与电脑接收器的空闲限制一致。普通请求仍为 10 秒，文件仍受 120 秒总时长限制。确定性回归将普通请求设为 20 毫秒，上传响应设为 500 毫秒。后片先到、前片请求体延迟 100 毫秒时，两片均成功且文件字节一致。如果前片始终未到，等待约 504 毫秒后返回 503 并取消临时上传。取消后再提交迟到分片会被拒绝。

本轮接收器、分片大小、超时、能力协商和真实 HTTP 压缩共 22 项测试全部通过，日志为 `/tmp/upload-verify-final.log`。临时逐阶段计时日志已移除，未执行 Git 提交或发布。后续 main 集成和统一发布由主聊天继续，原 owner/model 任务已经暂停。

新聊天附件首发也已接入每文件能力刷新、两片并发和首片压缩收益检测。保留创建标识与已暂存附件索引，失败后沿用同一次准备的聊天；6 项测试覆盖提交顺序、降级、取消和设备切换。新建聊天在创建确认前仍显示原有发送状态，尚未实现临时聊天气泡。
